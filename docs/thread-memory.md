# 内存的线程归属与回收

本文定义 FStore 的目标设计约束：**哪个固定 OS 线程申请内存，就由哪个 OS 线程执行对应对象的析构和内存释放。** 当前实现尚未完全满足这一约束；下文列出了已经确认的差距。此文不能作为现有版本已经实现同线程回收的声明。

## 约束范围

默认约束 FStore 管理的请求上下文、任务节点、数据缓冲区、容器及其节点、Chunk/PG 元数据、文件版本和 SDK 异步请求状态。线程身份指固定 OS 线程，不是 bthread、逻辑 worker 编号、CPU 编号或内存池编号。bthread 可能在不同 OS 线程上恢复执行，不能据此建立分配/释放归属。

bRPC/Protobuf 的内存由框架管理。FStore 创建的自定义 attachment 缓冲区和自定义回调对象属于上述约束范围；框架内部的 IOBuf block、协议解析对象和 RPC 生命周期对象不能因为外层使用线程内存池就宣称满足约束。如果需要把保证扩大到整个进程，必须同时审核和改造这些依赖的分配、回收与线程退出机制。

## 必须成立的不变量

1. 分配时确定 owner，存活期间不转移内存归属。任务迁移不等于内存归属迁移。
2. owner 执行申请、构造、析构、归还本地池、底层 free/delete；其他线程只持有有明确有效期的借用或句柄。
3. 跨线程的最后一个引用只能提交回收通知，不能就地析构。只把 `free` 放回 owner 而让 `std::string`、`std::vector`、`std::function` 等成员在其他线程析构，仍然不合格。
4. 回收通知本身不申请堆内存、不失败、不因队列满而回退到跨线程释放。回收节点嵌入原对象，且只能入队一次。
5. 普通完成、异常、超时、取消、连接关闭、重复回调防护和服务退出遵循同一规则。不能把错误处理作为例外。
6. owner 必须比其全部对象活得更久。不能在线程已经退出后再依赖 TLS 内存池、复用的线程 ID 或其他线程代为清理。

## 执行模型

每个固定工作线程有自己的内存池、待处理任务和回收队列。普通跨线程消息尽量只携带操作类型、数值参数、请求 ID 和借用指针；实际请求上下文和可变缓冲区由接收它的 owner 线程申请。不能在 RPC 入口先构造持有堆内存的闭包，再把闭包移动给存储线程销毁。

同线程完成时直接在本地回收；异线程完成时通过 intrusive MPSC 队列送回 owner。队列采用 release/acquire 发布关系；最后一个使用者发布回收通知后不得再访问对象。owner 批量取出通知、执行析构并归还自己的池。可以采用 SPSC 队列优化已知的固定线程对，但不能把多发送者误当成单发送者。

例如读响应：

```text
存储线程 W                         bRPC 发送/完成线程
    申请并填充 buffer
    借出 buffer ----------------------> 发送数据
    继续处理其他请求                    完成最后一次使用
    回收队列 <------------------------- 归还通知（不 delete）
    析构并归还本地池
```

发出通知的时机必须是 transport 不再引用缓冲区的时刻；不能在 RPC 超时或调用 `done->Run()` 时就假定发送数据已经用完。若同一缓冲区被多个副本或多个发送操作共享，要等所有使用者退出再归还。

回收队列不参与在线/复制/回收站的 8:1:1 数据限流；回收不产生新数据 I/O，限流它会阻碍释放并可能造成关闭死锁。每轮工作循环处理有界批量的回收通知，休眠线程可被回收通知唤醒；空闲时也必须继续回收。

队列节点复用原对象不代表内存占用无界可接受：各 owner 按在途对象和借出字节设置上限，慢客户端或慢回调达到上限后对新工作施加背压。不能通过丢弃回收通知解决压力。

## 组件归属

| 对象 | owner 与回收规则 |
|---|---|
| 在线请求上下文、乱序等待项、工作队列节点 | 固定存储 worker 创建和销毁；RPC 入口传递不拥有业务堆内存的描述符 |
| 读响应缓冲区 | 执行读取的 worker 分配；attachment 最后释放回调只归还句柄 |
| 限流等待节点 | 申请节点的固定执行线程为 owner；调度线程只调度并返回授予/拒绝结果，不销毁节点或拥有资源的回调 |
| 复制任务、接收会话、CRC 与分块缓冲区 | 固定复制 worker 持有；网络完成与超时清理都投递给会话 owner |
| Chunk/PG 可变元数据及容器节点 | 明确分片 owner，插入、替换、删除和最终容器销毁都在该线程完成；跨分片操作通过消息协调 |
| 只读文件版本 | 创建线程持有归属；最后一个跨线程读者退出后归还版本，owner 销毁对象并关闭 FD；读者退出前不得回收 |
| SDK 多副本请求状态 | SDK 固定 I/O worker 创建；回调投递完成事件。提前满足 frozen/quorum 后，未完成调用仍被跟踪，最后完成不直接销毁 Batch |
| FMaster 可变拓扑、恢复任务与目录快照 | 由明确的元数据执行线程管理，探测和 RPC 完成投递消息；不能依赖全局 mutex 推导出同线程生命周期 |
| 进程级预分配的描述符数组与不可变配置 | 由启动线程创建，并在所有使用线程退出之后由同一启动线程销毁；线程本地可变容器不适用这一例外 |

从调用者传入的 `IOBuf` 或其他缓冲区取得引用，不会改变其原有归属。SDK 必须明确借用的有效期；需要独立生命周期时，在目标 owner 上复制。不能靠移动拥有堆内存的对象，把原调用线程的分配冒充为目标线程的分配。

初次建立本地容器时，必须在对应 worker 内构造；退出前也在 worker 内销毁。仅让主线程创建 `Worker[]`，然后由 worker 扩容内部 map/list，最后在主线程析构数组，不满足容器内部内存的同线程回收约束。

## 退出顺序

1. 停止接收新工作，阻止新的外借引用。
2. 让在途操作完成或取消，但继续运行网络完成处理、业务 owner 和回收队列。
3. 等待所有外借对象归还，并在 owner 上排空回收队列、销毁本地对象和容器。
4. 确认 owner 的 outstanding 计数为零，再销毁本地池并退出线程。
5. join 完成后，启动线程释放自己申请的共享控制结构。

等待归还期间不能先停止产生完成通知所需的网络线程，也不能先 join owner。若调用方长期持有返回的数据，关闭必须等待这些借用结束，或者通过明确的 API 生命周期契约要求先释放；不能静默改为异线程释放。超时只能报告未完成对象，不能绕过归属规则。

## 当前代码的已知差距

| 代码路径 | 当前行为 |
|---|---|
| `Service::ReadChunk` | worker 分配 `char[]`，attachment 回调直接 `delete[]`，回调线程不保证相同 |
| `CountedDone` | RPC 线程分配，执行完成的线程 `delete this` |
| `Service::admit / work` | 分配 Submission 的线程可能是 RPC 或限流线程，worker 负责删除 |
| `TrafficLimiter::enqueue / finish` | 调用者分配 Request，dispatcher 销毁 Request 和 completion |
| `Job`、复制 `sends_` | 拥有资源的 `std::function` 跨线程移动和析构 |
| `Worker` 内部容器 | 主要在 worker 上申请节点，容器的最终销毁不保证在 worker 上 |
| `ChunkStore` 与 `PGInventory` | 容器和共享版本在不同调用线程增删，最后一个引用释放不保证回到创建线程 |
| `ReplicatedChunkClient::read_chunk` | Batch 在调用线程创建，提前返回后可能由最后一个 RPC 回调销毁 |

这些路径需要统一调整执行模型。只修读缓冲区或换成普通对象池不能满足整体约束；无锁队列也不自动保证对象的释放线程。

## 验收要求

开发构建记录分配的 owner token、实际 OS 线程身份和对象生命周期，底层释放以及对象析构均校验归属。token 必须区分线程的不同生命周期，不能仅依赖可能复用的 TID。

测试至少覆盖同线程释放、多生产者归还、批量回收、空闲唤醒、最后一个异线程引用、读缓冲区跨发送回调、限流取消/超时、SDK quorum 提前返回和迟到回调、修复中断、文件版本替换，以及关闭时仍有在途对象。将对象的动态成员和 shared_ptr 控制块纳入检查，验证无泄漏、无重复回收、无 UAF，关闭后 outstanding 为零。

性能验收同时观察吞吐、P99、回收队列长度、借出字节数和停止耗时。同线程回收有利于线程本地分配器，但增加通知和回收排队，不预先承诺一定提高吞吐。
